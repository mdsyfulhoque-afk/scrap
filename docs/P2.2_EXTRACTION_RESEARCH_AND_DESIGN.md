# P2.2 Extraction / Canonical Representation - Research and Design Report

**Phase:** P2.2 — Extraction / Canonical Representation  
**Status:** RESEARCH/DESIGN  
**Date:** 2026-08-17  
**Baseline:** P2.1 VERIFIED (commit cd46ea1)

---

## Executive Summary

P2.2 is responsible for transforming raw materialized artifacts from Phase 1 into structured, canonical representations suitable for downstream processing (normalization, quality assessment, deduplication, dataset generation). This stage must handle multiple input formats deterministically while preserving provenance, supporting reproducibility, and maintaining clear error classification boundaries.

**Key Design Decision:** P2.2 focuses on structural extraction and format conversion, NOT content normalization or quality assessment. The canonical representation preserves sufficient information for downstream stages while establishing a clean boundary between raw acquisition and processed representation.

## 1. What Exactly Enters P2.2?

**Input: `MaterializationResult` from P2.1**

```python
@dataclass
class MaterializationResult:
    processing_job_id: str          # P2.1 job that materialized this artifact
    artifact_id: str                 # Phase 1 artifact UUID
    resource_id: str                 # Phase 1 resource UUID
    fetch_id: str                    # Phase 1 fetch UUID
    source_url: str                  # Original URL
    raw_object_key: str             # MinIO object key
    raw_data: bytes                 # Raw bytes from MinIO
    checksum_sha256: str             # SHA-256 of raw_data
    checksum_verified: bool          # Whether checksum verification passed
    materialized_at: str             # ISO timestamp
```

**Additional Context from Database:**
- `artifacts.content_type` - HTTP Content-Type header
- `artifacts.metadata` - Phase 1 metadata (redirects, encoding hints, etc.)
- `fetches.headers` - Original HTTP headers
- `fetches.http_status` - HTTP status code

**Entry Boundary:**
- P2.2 receives raw bytes with full provenance chain
- No transformation has occurred since acquisition
- Original checksum is preserved and verified
- All Phase 1 metadata is accessible

## 2. What Exactly Leaves P2.2?

**Output: `ExtractionResult` (new model)**

```python
@dataclass
class ExtractionResult:
    processing_job_id: str          # P2.2 extraction job
    source_artifact_id: str         # Source artifact UUID
    extraction_method: str          # Method used (e.g., "trafilatura", "raw_passthrough")
    input_format: str               # Detected input format (e.g., "html", "json", "plain_text")
    canonical_text: str | None      # Extracted text content (None if extraction failed)
    canonical_metadata: dict        # Extraction metadata (title, author, dates, etc.)
    structured_data: dict | None    # Parsed structured data (for JSON/XML/CSV)
    extraction_version: str         # Version of extraction logic
    error_category: str | None     # Error classification if failed
    error_message: str | None       # Detailed error message if failed
    extraction_timestamp: str       # ISO timestamp of extraction
    provenance_preserved: bool      # Whether full provenance was retained
    byte_offset_info: dict | None   # Optional byte offset mapping for debugging
```

**Exit Boundary:**
- Canonical text representation (UTF-8 normalized)
- Extracted metadata preserved in structured form
- Structured data for formats that support it (JSON/XML/CSV)
- Clear success/failure classification
- Full provenance linkage maintained
- Extraction versioning for reproducibility

## 3. Which Formats Are Supported in P2.2?

### Primary Supported Formats (P2.2 Scope)

| Format | Content-Type Patterns | Extraction Method | Complexity |
|--------|---------------------|-------------------|------------|
| **HTML** | text/html, application/xhtml+xml | Trafilatura | Medium |
| **Plain Text** | text/plain, text/* (fallback) | Raw passthrough + encoding normalization | Low |
| **JSON** | application/json, application/ld+json | JSON parser | Low |
| **CSV** | text/csv, application/csv | CSV parser | Low |
| **XML** | text/xml, application/xml, */*+xml | XML parser | Medium |
| **Markdown** | text/markdown, text/x-markdown | Markdown-to-text | Low |

### Secondary Formats (Deferred to Future P2.2 Enhancements)

| Format | Reason for Deferral |
|--------|-------------------|
| **PDF** | Requires heavy dependencies (PyPDF2, pdfplumber), complex layout analysis |
| **Word Documents** | Requires python-docx, complex structure handling |
| **Excel** | Requires openpyxl, binary format complexity |
| **Images** | Requires OCR (tesseract), falls outside text extraction scope |
| **Audio/Video** | Requires transcription services, outside current scope |

### Unsupported Binary Formats

**Handling Strategy:**
- Classify as `unsupported_format` error
- Preserve raw bytes in metadata for potential future processing
- Record content-type and size for debugging
- Do NOT fail the entire processing pipeline
- Allow downstream stages to skip unsupported formats

**Error Categories:**
- `unsupported_format` - Known binary formats (images, audio, video, archives)
- `unknown_format` - Content-type not recognized or missing
- `corrupted_format` - Format recognized but parsing failed

## 4. Which Libraries Should Be Used and Why?

### HTML Extraction: Trafilatura

**Choice:** `trafilatura` (primary), with `beautifulsoup4` as fallback

**Rationale:**
- **Trafilatura:** Designed specifically for web content extraction
  - Main content extraction (boilerplate removal)
  - Metadata extraction (title, author, date)
  - Comments and navigation removal
  - Language-agnostic approach
  - Active maintenance, good documentation
  - Lightweight dependency footprint
- **BeautifulSoup4:** Fallback for malformed HTML
  - Robust parsing of broken HTML
  - Flexible selectors
  - Widely used and stable

**Alternatives Considered:**
- `readability-lxml` (Mozilla-based): Good but heavier dependency
- `inscriptis`: Table-focused, less general-purpose
- `newspaper3k`: Too broad, includes download logic (duplicate with Phase 1)

### JSON/XML/CSV: Standard Library

**Choice:** Python standard library (`json`, `xml.etree.ElementTree`, `csv`)

**Rationale:**
- **No external dependencies** for core formats
- **Deterministic behavior** across Python versions
- **Well-tested** and stable
- **Sufficient** for structured data extraction
- **Performance** is acceptable for our scale

### Markdown: markdown-it-py

**Choice:** `markdown-it-py` (pure Python)

**Rationale:**
- CommonMark compliant
- No C extensions (portability)
- Extensible for custom parsing
- Better than `markdown` (older, less maintained)

### Encoding Detection: chardet

**Choice:** `chardet` (already likely available via requests dependency)

**Rationale:**
- Robust encoding detection
- Handles malformed encodings
- Fallback mechanisms for ambiguous cases
- Industry standard for web content

### Library Summary

| Format | Library | Dependency Status |
|--------|---------|------------------|
| HTML | trafilatura, beautifulsoup4 | NEW (add to pyproject.toml) |
| JSON | json (stdlib) | EXISTING |
| XML | xml.etree.ElementTree (stdlib) | EXISTING |
| CSV | csv (stdlib) | EXISTING |
| Markdown | markdown-it-py | NEW (add to pyproject.toml) |
| Encoding | chardet | EXISTING (via requests) |

## 5. What Is the Canonical Representation?

### Canonical Text Representation

**Definition:** UTF-8 normalized string with structural markers removed

**Characteristics:**
- **Encoding:** UTF-8 (NFC normalization)
- **Line Endings:** Unix-style (`\n`)
- **Whitespace:** Preserved for structure, normalized for prose
- **Control Characters:** Removed (except `\n`, `\t`)
- **Unicode:** NFC normalization for canonical equivalence
- **Structure:** HTML/XML tags removed, text content preserved
- **Metadata:** Extracted and stored separately, not inline

### Canonical Metadata Structure

```python
{
    "title": str | None,              # Document title
    "author": str | None,             # Author/creator
    "date": str | None,               # Publication date (ISO format)
    "description": str | None,        # Summary/description
    "language": str | None,          # Detected language (ISO 639-1)
    "content_type": str,              # Original content-type
    "format": str,                    # Detected format (html, json, etc.)
    "encoding": str,                  # Detected encoding
    "size_bytes": int,                # Original raw size
    "text_length": int,               # Extracted text length
    "extraction_method": str,         # Method used
    "extraction_version": str,        # Version identifier
    "has_structured_data": bool,      # Whether structured data exists
    "byte_offsets": dict | None,      # Debug mapping (optional)
    "extraction_warnings": list[str], # Non-fatal warnings
}
```

### Structured Data (JSON/XML/CSV)

**Format-Specific Handling:**

**JSON:**
- Preserve original structure
- Convert to canonical Python dict
- Store in `structured_data` field
- Text extraction: `json.dumps(canonical_dict, ensure_ascii=False)`

**XML:**
- Parse to ElementTree
- Extract text content recursively
- Preserve attribute structure in metadata
- Store parsed XML in `structured_data` (dict representation)

**CSV:**
- Parse with csv module
- Detect headers
- Convert to list of dicts
- Text extraction: Join rows with newlines

### Canonical Representation Invariants

1. **Deterministic:** Same input → same output (given same extraction version)
2. **Reversible:** Can reconstruct approximate original from canonical + metadata
3. **Format-Agnostic:** Downstream stages don't need to know original format
4. **Provenance-Rich:** Full chain back to Phase 1 preserved
5. **Error-Classified:** Clear distinction between success and failure modes
6. **Versioned:** Extraction method versioned for reproducibility

## 6. How Is Provenance Retained?

### Provenance Chain Extension

**P2.2 extends the existing Phase 1 → P2.1 chain:**

```
Phase 1: resource → fetch → artifact (MinIO)
    ↓
P2.1: artifact → processing_job → materialization_result
    ↓
P2.2: materialization_result → extraction_job → extraction_result
```

### Provenance Preservation Mechanisms

**Database Linkages:**
- `ExtractionResult.source_artifact_id` → `artifacts.id`
- `ExtractionResult.processing_job_id` → `processing_jobs.id`
- `processing_jobs.source_artifact_id` → `artifacts.id`

**Metadata Preservation:**
- All Phase 1 metadata copied to extraction metadata
- Original content-type preserved
- Original encoding preserved
- Original checksum preserved
- Source URL preserved
- Fetch timestamp preserved

**Reproducibility Links:**
- `extraction_version` records exact extraction logic
- `extraction_timestamp` for temporal reference
- Configuration preserved in processing job config

### Provenance Query Example

```sql
-- Full provenance for extracted document
SELECT 
    e.id as extraction_id,
    e.canonical_text,
    e.extraction_method,
    e.extraction_version,
    pj.id as processing_job_id,
    pj.config as extraction_config,
    a.id as artifact_id,
    a.checksum_sha256 as original_checksum,
    a.object_key as minio_location,
    f.id as fetch_id,
    f.http_status,
    r.url as source_url,
    r.domain
FROM extraction_results e
JOIN processing_jobs pj ON e.processing_job_id = pj.id
JOIN artifacts a ON pj.source_artifact_id = a.id
JOIN fetches f ON a.fetch_id = f.id
JOIN resources r ON f.resource_id = r.id
WHERE e.id = :extraction_id;
```

## 7. How Is Reproducibility Guaranteed?

### Deterministic Extraction

**Versioning Strategy:**
- Extraction logic versioned as semantic version (e.g., "1.0.0")
- Version stored in `extraction_version` field
- Library versions recorded in processing job config
- Configuration parameters recorded in processing job config

**Deterministic Behavior:**
- No random elements in extraction
- No time-dependent behavior
- No external network calls (all local)
- Fixed fallback order for libraries
- Encoding detection with fallback chain

### Configuration Recording

**Processing Job Config Structure:**
```python
{
    "extraction": {
        "version": "1.0.0",
        "method": "trafilatura",
        "fallback_methods": ["beautifulsoup4"],
        "encoding_detection": "chardet",

            "unicode_form": "NFC",

        "markdown-it-py": "3.x.x",

    }

```

### Reproducibility Verification

**Checksum Preservation:**
- Original artifact checksum preserved

- Should produce identical metadata

## 8. How Are Extraction Failures Classified?

### Error Category Taxonomy

**Primary Error Categories:**

| Category | Description | Recovery Strategy |
|----------|-------------|-------------------|
| `unsupported_format` | Format not supported in P2.2 | Skip, preserve raw bytes |
| `unknown_format` | Content-type not recognized | Attempt heuristics, then skip |
| `corrupted_format` | Format recognized but parsing failed | Skip, record corruption details |
| `encoding_error` | Encoding detection/decoding failed | Try fallback encodings, then skip |
| `size_limit_exceeded` | Document too large for extraction | Skip, record size |
| `memory_limit_exceeded` | Extraction exceeded memory bounds | Skip, record memory usage |
| `timeout` | Extraction took too long | Skip, record timeout |
| `library_error` | Extraction library raised unexpected error | Retry with fallback, then skip |
| `empty_content` | Extraction succeeded but produced no text | Record as empty, allow downstream handling |

### Error Severity Levels

**Non-Fatal (Continue Processing):**
- `unsupported_format` - Expected for binary content
- `empty_content` - May be valid for some use cases
- `size_limit_exceeded` - Configured limit, not actual error

**Fatal (Stop Processing This Document):**
- `corrupted_format` - Cannot recover
- `encoding_error` (after fallbacks) - Cannot decode
- `memory_limit_exceeded` - Resource constraint
- `timeout` - Resource constraint
- `library_error` (after fallbacks) - Unexpected failure

### Error Recording

**Database Schema (proposed):**
```sql
ALTER TABLE extraction_results ADD COLUMN error_category TEXT;
ALTER TABLE extraction_results ADD COLUMN error_message TEXT;
ALTER TABLE extraction_results ADD COLUMN error_details JSONB;

-- error_details structure:
{
    "original_error": str,           # Exception type/message
    "fallback_attempted": bool,      # Whether fallback was tried
    "fallback_method": str | None,   # Which fallback was used
    "encoding_attempts": list[str],  # Encodings tried
    "library_versions": dict,        # Library versions at failure
    "resource_limits": dict          # Memory/time limits at failure
}
```

## 9. How Are Malformed Documents Handled?

### HTML Malformation Handling

**Strategy:**
1. **Primary:** Trafilatura (robust to many HTML issues)
2. **Fallback 1:** BeautifulSoup4 with lenient parser
3. **Fallback 2:** Regex-based text extraction (last resort)
4. **Failure:** Classify as `corrupted_format`, preserve raw HTML

**Specific Issues Handled:**
- Unclosed tags
- Mismatched tags
- Invalid nesting
- Missing DOCTYPE
- Character encoding issues
- Script/style tag content
- Comments and navigation elements

### JSON/XML Malformation Handling

**JSON Strategy:**
1. **Primary:** Standard JSON parser
2. **Fallback:** Try to fix common JSON issues (trailing commas, comments)
3. **Failure:** Classify as `corrupted_format`, preserve raw bytes

**XML Strategy:**
1. **Primary:** ElementTree with error recovery
2. **Fallback:** lxml with recovery mode (if available)
3. **Failure:** Classify as `corrupted_format`, preserve raw bytes

### Encoding Malformation Handling

**Strategy:**
1. **Primary:** Use content-type charset hint
2. **Fallback 1:** chardet detection
3. **Fallback 2:** Try common encodings (UTF-8, Latin-1, Windows-1252)
4. **Fallback 3:** Try with error handling (replace/skip)
5. **Failure:** Classify as `encoding_error`, preserve raw bytes

**Malformed Byte Handling:**
- Replace invalid sequences with U+FFFD (replacement character)
- Record number of replacements in metadata
- If replacements exceed threshold, classify as error

### Size/Resource Malformation Handling

**Size Limits:**
- Configurable maximum document size (default: 10MB)
- Configurable maximum extraction time (default: 30s)
- Configurable maximum memory usage (default: 100MB)

**Handling Strategy:**
- Stream processing for large documents where possible
- Chunked processing for very large documents
- Skip documents exceeding hard limits
- Record limit details in error metadata

## 10. How Is Extraction Versioning Handled?

### Semantic Versioning for Extraction Logic

**Version Format:** `MAJOR.MINOR.PATCH`

- **MAJOR:** Breaking changes to canonical representation
- **MINOR:** New format support, non-breaking changes
- **PATCH:** Bug fixes, performance improvements

**Initial Version:** `1.0.0`

### Version Registry

**Database Table (proposed):**
```sql
CREATE TABLE extraction_versions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    version TEXT NOT NULL UNIQUE,
    description TEXT,
    config JSONB NOT NULL,
    library_versions JSONB NOT NULL,
    supported_formats TEXT[] NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deprecated_at TIMESTAMPTZ
);
```

**Version Recording:**
- Each extraction job records version used
- Version lookup table available for reproducibility
- Deprecated versions marked but preserved

### Migration Strategy

**When Extraction Logic Changes:**
1. **Bump version** according to semantic versioning
2. **Register new version** in extraction_versions table
3. **Old versions remain available** for re-processing
4. **Default to latest version** for new extractions
5. **Allow explicit version selection** for reproducibility

**Re-processing with Old Version:**
- User can specify extraction_version in job config
- Enables historical reproducibility
- Supports A/B testing of extraction methods

## 13. What Should Remain Raw and Immutable?

### Immutable Artifacts

**Phase 1 Artifacts (MinIO):**
- **NEVER MODIFIED** after Phase 1
- Original bytes preserved indefinitely
- Checksum verification on every access
- Immutable foundation for all processing

**Raw Materialization Results:**
- Raw bytes from P2.1 are immutable
- Original checksum preserved
- No transformation in P2.1

### P2.2 Immutable Elements

**Original Content-Type:**
- Preserved in metadata
- Never modified
- Used for format detection

**Original Encoding:**
- Preserved in metadata
- Used for reproducibility
- Not modified after detection

**Original Checksum:**
- Preserved from Phase 1
- Used for integrity verification
- Never modified

**Source URL:**
- Preserved from Phase 1
- Never modified
- Used for provenance

### Mutable Elements (Justified)

**Canonical Text:**
- Derived from raw bytes
- Deterministic transformation
- Reproducible from original
- Modified only by extraction logic changes (versioned)

**Canonical Metadata:**
- Extracted from content
- Enhanced with extraction metadata
- Reproducible from original + extraction version

**Structured Data:**
- Parsed representation
- Reproducible from original
- Modified only by parser changes (versioned)

## 14. What Belongs in Later Normalization/Dataset-Generation Stages?

### P2.3 (Normalization) - NOT in P2.2

**Excluded from P2.2:**
- Unicode normalization beyond NFC
- Whitespace normalization (beyond line ending standardization)
- Case normalization
- Accent/diacritic removal
- Special character handling
- Text cleaning beyond boilerplate removal

**Rationale:**
- P2.2 focuses on extraction, not normalization
- Different normalization strategies may be needed for different use cases
- Keep extraction independent of normalization preferences

### P2.4 (Language Identification) - NOT in P2.2

**Excluded from P2.2:**
- Language detection (fastText, etc.)
- Language confidence scoring
- Language filtering
- Language-specific processing

**Rationale:**
- Language identification is a separate concern
- May require different models/approaches
- Should operate on canonical text, not raw bytes

### P2.5 (Quality Assessment) - NOT in P2.2

**Excluded from P2.2:**
- Quality heuristics (line punctuation, short lines, etc.)
- Repetition detection
- Statistical quality measures
- Quality scoring
- Quality filtering

**Rationale:**
- Quality assessment operates on canonical text
- Different quality thresholds for different use cases
- Should be independent of extraction

### P2.6 (Exact Deduplication) - NOT in P2.2

**Excluded from P2.2:**
- SHA-256 hashing of canonical text
- Duplicate detection
- Duplicate removal
- Deduplication indexing

**Rationale:**
- Deduplication operates on canonical text
- May be applied at different stages
- Should be independent of extraction

### P2.8+ (Document Segmentation, Metadata Enrichment, Dataset Generation) - NOT in P2.2

**Excluded from P2.2:**
- Document segmentation
- Advanced metadata enrichment
- Dataset record construction
